# Chapter 13 — A Philosophy of Streaming Systems

**DDIA 2nd Edition, Chapter 13**

> "If a thing be ordained to another as to its end, its last end cannot consist in the preservation of its being. Hence a captain does not intend as a last end, the preservation of the ship entrusted to him, since a ship is ordained to something else as its end, viz. to navigation."

## Topics

- Data integration: no single tool fits all access patterns, mapping software to circumstances, combining specialized tools (OLTP database + full-text search index, analytics, caches, ML systems, notifications)
  - Reasoning about dataflows: being explicit about inputs and outputs, systems of record vs derived representations, funneling all writes through a single ordering system, CDC vs event sourcing (the total order matters more than the mechanism), state machine replication, deterministic and idempotent derivation for fault recovery
  - Derived data vs distributed transactions: atomic commit vs deterministic retry + idempotence, transactions give read-your-writes while derived systems are asynchronous by default, XA's poor fault tolerance and performance, log-based derived data as the most promising integration approach
  - The limits of total ordering: single-leader throughput bottleneck, ambiguous ordering across log shards, separate leaders per datacenter, microservices with no shared durable state, offline-capable clients seeing events in different orders, total order broadcast as equivalent to consensus
  - Ordering events to capture causality: the unfriend-then-message example (a notification service joining messages against a stale friend list), logical timestamps, logging an event to record what the user saw before deciding, conflict resolution algorithms and their limits when actions have external side effects
- Batch and stream processing for maintaining derived state: functional flavor (deterministic pure functions, immutable inputs, append-only outputs), stream processing as batch plus managed fault-tolerant state, asynchrony as fault containment (vs distributed transactions amplifying failures), asynchronous maintenance of cross-shard secondary indexes
  - Reprocessing data for application evolution: stream processing for low-delay updates, batch reprocessing to restructure a dataset into a completely different model, the railway gauge migration analogy, maintaining old and new schemas side by side as independently derived views, gradual user migration, reversibility at every stage
  - Unifying batch and stream processing: the lambda architecture and its problems, the kappa architecture, replaying historical events through the same engine (log-based brokers, reading from distributed filesystems/object storage), exactly-once semantics, windowing by event time not processing time (Apache Beam on Flink or Google Cloud Dataflow)
- Unbundling databases: databases, batch/stream processors, and operating systems as information management systems, the Unix philosophy (low-level, pipes, bytes) vs the relational philosophy (high-level declarative queries, transactions), NoSQL as Unix-esque distributed OLTP
  - Composing data storage technologies: secondary indexes, materialized views, replication logs, and full-text indexes as database features vs derived data systems; CREATE INDEX as reprocessing an existing dataset to derive a new view; the whole organization's dataflow as one huge "meta-database"; batch/stream processors as elaborate triggers, stored procedures, and materialized-view maintenance
  - Federated databases (unifying reads: polystores, PostgreSQL foreign data wrappers, Trino) vs unbundled databases (unifying writes: CDC and event logs as unbundled index maintenance)
  - Making unbundling work: why synchronizing writes is the harder problem, asynchronous event log with idempotent writes vs distributed transactions across heterogeneous systems, loose coupling at the system level (log buffering contains faults) and the human level (teams own components independently)
  - Unbundled vs integrated systems: unbundling is breadth not depth, the operational cost of many moving parts, premature scaling as premature optimization, use a single product if it satisfies your needs, improving composition tools (Debezium, Kafka's protocol as a de facto standard, incremental view maintenance engines)
- Designing applications around dataflow: the spreadsheet analogy (VisiCalc, automatic recalculation of derived values with durability and fault tolerance added)
  - Application code as a derivation function: secondary indexes, full-text search (stemming, synonyms, inverted indexes), ML models derived from training data, UI caches; where cookie-cutter derivation ends and custom code begins
  - Separation of application code and state: why databases make poor application deployment environments, stateless services + database as mutable shared variable, "separation of Church and state", the inability to subscribe to changes (polling as the default, observer pattern)
  - Dataflow between state changes and application code: stable message ordering and fault-tolerant processing as requirements for derived data, stream operators composed like Unix pipes
  - Stream processors vs microservices: one-directional asynchronous message streams vs synchronous request/response, the currency exchange rate example (subscribing to a stream of rate updates vs querying a rate service), replacing RPC with a local database lookup plus stream join, time-dependent joins
- Observing derived state: the write path (eager, precomputed) vs the read path (lazy, on demand), derived datasets as the meeting point
  - Materialized views and caching: full-text index vs precomputing all search results vs grep-like scanning; caches, indexes, and materialized views as devices for shifting the boundary between write path and read path
  - Stateful, offline-capable clients: single-page apps and mobile apps with local state, offline-first, on-device state as a cache of server state, pixels as a materialized view of model objects
  - Pushing state changes to clients: polling vs server-sent events (EventSource) and WebSockets, extending the write path all the way to end-user devices, consumer offsets to catch up after disconnection (each device as a small subscriber)
  - End-to-end event streams: reactive UI tools (React, Elm), state changes flowing from one device through logs, processors, and derived systems to another device's UI, why request/response assumptions are deeply ingrained, moving toward publish/subscribe dataflow
  - Reads are events too: queryable stream processor state, routing read events through the log, serving requests as a stream-table join between queries and the database, logging reads for causal tracking and data provenance
  - Multishard data processing: Storm's distributed RPC, the fraud-prevention example (joining reputation scores across differently sharded datasets)
- Aiming for correctness: stateful systems remember forever, the weakness of transaction foundations (confusing weak isolation levels), vague appeals to "embracing weak consistency", Jepsen findings vs claimed guarantees
  - The end-to-end argument for databases: serializable transactions don't save you from application bugs, immutability as a mistake-recovery aid, exactly-once execution through idempotence, duplicate suppression at each layer (TCP sequence numbers, transaction retries after connection loss, the nonidempotent money transfer, browser POST retries), uniquely identifying requests end to end (client-generated request IDs + uniqueness constraints), the requests table as an event log, the Saltzer/Reed/Clark end-to-end argument applied to duplicate suppression, checksums, and encryption
  - Enforcing constraints: uniqueness constraints require consensus, single-leader ordering, scaling by sharding on the constrained value, why async multi-leader replication is ruled out; uniqueness in log-based messaging (route conflicting writes to the same log shard, a single-threaded stream processor decides deterministically, clients wait on an output stream)
  - Multishard request processing: the payment example (source account, destination account, fees) executed as several differently sharded stages without atomic commit, atomicity from a single atomic log append, at-least-once delivery + deterministic processors + request-ID deduplication, equivalence to exactly-once
  - Timeliness and integrity: unbundling "consistency" into timeliness (up-to-date reads; temporary, fixed by waiting) vs integrity (no corruption, no loss; permanent if violated), integrity over timeliness in most applications, how dataflow systems decouple the two, the mechanisms that preserve integrity (atomic single-message writes, deterministic derivation, end-to-end request IDs, immutability and reprocessing)
  - Loosely interpreted constraints: overselling stock, airline/hotel overbooking, overdrafts, compensating transactions and the cost of apology, optimistic writes with after-the-fact validation
  - Coordination-avoiding data systems: strong integrity without atomic commit, linearizability, or synchronous cross-shard coordination; multi-datacenter multi-leader operation with weak timeliness but strong integrity; coordination as a trade between apologies for inconsistency and apologies for outages
  - Trust, but verify: system models as probabilities not binaries, corruption in memory, disk, and network, database bugs (MySQL uniqueness violations, PostgreSQL serializability bugs), auditing as integrity checking, HDFS/S3 background scrubbing, self-validating systems, designing for auditability (event sourcing gives deterministic, repeatable derivation; hashing event logs; rederiving state to verify), end-to-end integrity checks, tools (blockchains as Byzantine fault-tolerant append-only logs, Merkle trees, certificate transparency)

## Assignment

Design the dataflow architecture for an online marketplace backend built as an "unbundled database." The platform has one set of business facts — listings, orders, payments — that must be represented in many places: a system of record, a full-text search index, a per-user cache, an analytics feed, and a notifications service. Your system must keep all derived representations consistent with the system of record without distributed transactions, execute customer orders exactly once despite client retries and processor crashes, enforce business constraints (no double-claiming of a one-of-a-kind listing, no negative account balances) at scale, support restructuring a derived view without downtime, and detect data corruption before customers do.

1. **Theory pass** — conversational interview on derived data vs distributed transactions, the limits of total ordering, unbundling databases (federation vs unbundling, loose coupling), write path vs read path, the end-to-end argument, timeliness vs integrity, loosely interpreted constraints and compensating transactions, coordination avoidance, and auditability
2. **Design pass** — produce a `DESIGN.md`: decide what the system of record is and how events enter the system, design the log topology and sharding strategy and how it interacts with each constraint you must enforce, decide which constraints get synchronous enforcement and which are loosely interpreted with compensation (and justify the apology cost), design the derivation pipeline for each derived view (ordering, idempotence, fault recovery), design the end-to-end request ID flow from client to every derived system, specify what timeliness guarantees clients get and how (waiting on output streams vs eventual), define the reprocessing/migration strategy for evolving a derived view, and design the audit mechanism that verifies integrity of derived state. Include rejected alternatives with reasoning.
3. **Implementation pass** — build a working prototype that demonstrates an event log feeding at least two derived views, constraint enforcement under concurrent conflicting requests, duplicate suppression under client retries and processor crash/restart with at-least-once redelivery, rederiving a restructured view from the log while the old view keeps serving, and an integrity check that catches deliberately injected corruption in a derived view
4. **Review** — defend your reasoning in a reviewer session

## Scenario

You're a staff engineer at an online marketplace for collectibles and one-of-a-kind items. The platform hosts about 8 million active listings and processes around 40,000 orders per day, with sharp spikes when a popular seller drops a new collection. The architecture grew organically: a PostgreSQL system of record, an Elasticsearch cluster for search, a Redis cache for product pages and seller dashboards, a nightly ETL into the data warehouse, and a notifications service — each updated by application code making direct writes wherever data needs to go.

The team has been burned three times in the past two quarters:

1. **The drifting search index**: the checkout and listing services write to PostgreSQL and Elasticsearch separately, in whatever order their requests happen to land. After a partial deploy failure, roughly 120,000 listings were inconsistent between the database and the index — sold items still searchable, new listings invisible — and nobody noticed for three weeks because nothing checks that the index actually matches the database. This is the dual-write problem the chapter opens with: two storage systems, no single system deciding the order of writes, and no auditing to catch the drift.
2. **The double-charged drop**: during a high-profile collection drop, buyers on flaky mobile connections retried checkout when the confirmation page timed out. The payment logic runs in a serializable PostgreSQL transaction, but each retry was a brand-new request and a brand-new transaction, so the database happily executed both. 340 customers were charged twice, and 12 one-of-a-kind items were sold to two buyers each. Transactions at the database layer couldn't help — the duplicate had to be suppressed end to end, with a request identifier flowing from the buyer's device all the way to the write.
3. **The nine-hour migration**: restructuring the listing categories (a long-requested catalog change) required a maintenance window to rewrite the search index and rebuild the Redis cache from a hand-written backfill script. The script had a bug, the rebuilt cache served wrong prices for six hours, and rolling back was nearly as painful as going forward. There was no way to derive the new representation alongside the old one and switch over gradually, because there is no reprocessable log of what happened — only the current state.

Leadership has approved a redesign of how data flows through the platform. They want search, caches, analytics, and notifications to stay reliably in sync with the system of record; they want checkout to be safe under retries; and they want migrations and corruption checks to stop being heroics. They also want to know where you'll spend coordination — and where you deliberately won't, and what the business will have to apologize for when you don't.

Walk me through how you'd design the dataflow architecture for this marketplace.
