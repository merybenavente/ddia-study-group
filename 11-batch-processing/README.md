# Chapter 11 — Batch Processing

**DDIA 2nd Edition, Chapter 11**

> "A system cannot be successful if it is too strongly influenced by a single person. Once the initial design is complete and fairly robust, the real test begins as people with many different viewpoints undertake their own experiments."

## Topics

- Online vs offline systems: request/response vs batch jobs, throughput as the primary performance measure, jobs that run for minutes to days on a periodic schedule
  - The batch processing contract: read-only immutable inputs, output generated from scratch on every run, output as derived data, no side effects during processing
  - Benefits of immutability: human fault tolerance (roll back code and rerun), time travel in object stores and open table formats, minimizing irreversibility, reusing the same input files for multiple jobs, efficient resource usage
  - Limitations: downstream jobs wait for the whole job to finish, a single-byte input change forces full reprocessing
  - Historical arc: MapReduce (Google 2004, now largely obsolete), Hadoop, the shift to Spark/Flink and data warehouse query engines, Oozie/Azkaban replaced by Airflow/Dagster/Prefect, storage shifting from distributed filesystems (HDFS, GlusterFS, CephFS) to object stores (S3), BigQuery and Snowflake blurring the warehouse/batch line
- Batch processing with Unix tools: log analysis with a `cat | awk | sort | uniq -c | sort -rn | head` pipeline
  - Chain of commands vs custom program: the same analysis as a Python script with an in-memory hash table
  - Sorting vs in-memory aggregation: the job's working set, when a hash table fits in memory vs when sorting wins, spilling sorted segments to disk and merging them (mergesort's sequential access patterns), GNU `sort` handling larger-than-memory data and parallelizing across cores, single-machine limits
- Batch processing in distributed systems: frameworks as distributed operating systems — a filesystem, a scheduler, and programs connected through storage
  - Distributed filesystems: the OS filesystem layer analogy (block drivers, page cache, filesystem, VFS), large block sizes (HDFS 128 MB vs ext4 4 KB) and why they matter at petabyte scale, data nodes (HDFS DataNodes, glusterfsd), metadata services (Hadoop NameNode, 3FS on FoundationDB), distributed page caching, pluggable protocols (the S3 API as de facto standard; FUSE and NFS for POSIX integration, EFS)
  - Shared-nothing DFSs vs shared-disk NAS/SAN, commodity hardware and failure tolerance, block replication vs erasure coding (Reed–Solomon), comparison to RAID
  - Object stores: buckets, keys, and immutable objects; get/put with no file handles; "directories" as key-prefix convention, prefix listing vs directory listing, no empty directories; missing filesystem features (links, locking, atomic renames); optimization for large infrequent reads vs key-value stores; S3 Express One Zone; data locality (compute on the node holding the data) vs separation of storage and compute
  - Distributed job orchestration: what a job-start request contains (tasks, resources, credentials, executable location); task executors (YARN NodeManager, Kubernetes kubelet, cgroup isolation), resource managers (cluster state in ZooKeeper/etcd, scalability and availability bottlenecks), centralized schedulers, application-specific schedulers (YARN ApplicationMasters, Kubernetes operators)
  - Resource allocation: fairness vs efficiency, gang scheduling and deadlock, starvation, preemption costs, NP-hardness of optimal scheduling, practical heuristics (FIFO, dominant resource fairness, priority queues, capacity/quota scheduling, bin packing)
  - Scheduling workflows: DAGs of jobs, batch workflows vs durable execution engines, decoupling jobs by materializing output to a DFS/object store vs direct task-to-task data transfer with backpressure, per-job schedulers vs workflow schedulers (Airflow, Dagster, Prefect), 50–100-job workflows in real pipelines
  - Handling faults: task failures from hardware faults, network interruptions, and deliberate preemption; spot/preemptible instances and why batch jobs suit them; deleting partial output and retrying at individual-task granularity; the intermediate-state tradeoff — MapReduce materializes to the DFS, Spark keeps intermediate data in memory and recomputes from lineage, Flink checkpoints task snapshots
- Batch processing models
  - MapReduce: the four steps (parse records, map, sort, reduce), mapper and reducer contracts (stateless mappers, reducers iterating over grouped values), chaining jobs for multi-stage sorts, functional programming roots (map/fold, immutability enabling parallelism and retries), why raw MapReduce is laborious and slow (hand-written joins, file-based I/O preventing pipelining)
  - Dataflow engines: Spark and Flink (rooted in Dryad and Nephele), an entire workflow as one job, flexible operator assembly beyond map/reduce, sorting only where needed, operator fusion, locality optimizations, intermediate state in memory or local disk, pipelined execution, process reuse
  - Shuffling data: distributed sort over sharded input and output, hash-partitioning mapper output into per-reducer files, sorting within files via sorted segments and merging, reducers fetching and merge-sorting mapper output, "shuffle is not random," external shuffle services (BigQuery's in-memory shuffle)
  - Joins and grouping: joining a fact table (activity events / clickstream) with a dimension table (user database), shuffle bringing all records for a key to the same reducer, secondary sort, the sort-merge join, implementing group-by and aggregation with a second shuffle
  - Query languages: SQL as the lingua franca of batch processing, interactive/exploratory querying, cost-based query optimizers (Hive, Trino, Spark, Flink) choosing join algorithms and join order, niche languages (Pig, Morel, jq/JMESPath/JSONPath, Gremlin for graphs)
  - Convergence of batch frameworks and cloud data warehouses: batch systems adopting SQL and columnar formats (Parquet), warehouses adopting batch-style scheduling/fault tolerance/shuffling and DataFrame libraries (BigQuery DataFrames, Snowpark), workloads that resist SQL (iterative graph algorithms like PageRank, ML, multimodal AI data), cost tradeoffs
  - DataFrames: relational operators as function calls, local (Pandas, eager, indexed/ordered) vs distributed (Spark/Flink/Daft, lazy query plans, generally unordered), client- vs server-side execution, Apache Arrow as a shared columnar data model
- Batch use cases
  - ETL: embarrassingly parallel transformations, workflow schedulers with retries and built-in operators, debuggability of failed jobs, data mesh / data contracts / data fabric, pipelines and analytics sharing execution engines (SparkSQL, Trino, DuckDB)
  - Analytics: the data lakehouse (query engines over object storage, table formats like Iceberg, catalogs like Unity), pre-aggregation into OLAP cubes / data marts pushed to real-time OLAP systems (Druid, Pinot), ad hoc queries, BI tool integration (Tableau, Superset)
  - Machine learning: feature engineering, model training, batch inference; graph processing with the bulk synchronous parallel (Pregel) model (Giraph, GraphX, Gelly); LLM data preparation (text extraction, dedup, tokenization/embedding); ML-oriented frameworks (Kubeflow, Flyte, Ray); interactive notebooks
  - Serving derived data: why writing directly from batch tasks to a production database is a bad idea (per-record request overhead, overwhelming the database with parallel writers, losing the all-or-nothing output guarantee, duplicated output from retried tasks); pushing output through streams (Kafka) as buffer, fan-out, and security boundary (DMZ), completion notifications for atomic visibility; building whole databases in the batch job and bulk-loading them (TiDB Lightning, Pinot import jobs, RocksDB SST ingestion), atomic dataset swaps, hybrid stores (Venice)

## Assignment

Design and build a miniature distributed batch processing framework: an engine that takes sharded, immutable input files, runs user-supplied processing logic in parallel across multiple worker processes, and produces a complete output dataset — surviving worker crashes along the way. The framework must support the two operations this chapter identifies as foundational: grouping records by key and joining two large datasets, both of which require you to move data between workers. It must also uphold the batch processing contract: inputs are never mutated, partial output from failed tasks is never visible, and a completed job's output is the result of running every task exactly once — even when tasks crashed and were retried mid-run.

Your job is to decide how work is split into tasks, how data gets from one stage to the next, what happens when a task dies halfway through, and how the finished output is handed off — and to be able to defend every one of those decisions.

1. **Theory pass** — conversational interview on the batch processing contract (immutable inputs, derived output, human fault tolerance), sorting vs in-memory aggregation, distributed filesystems vs object stores, job orchestration and resource allocation, the shuffle, sort-merge joins, MapReduce vs dataflow engines, intermediate-state strategies (materialization vs recomputation vs checkpointing), and the hazards of serving derived data to production systems
2. **Design pass** — produce a `DESIGN.md` for the framework: choose a processing model and define the API user code programs against, decide how input is sharded and how task parallelism is determined, design the shuffle (partitioning, sorting, and how data moves between stages), choose a join strategy, decide how intermediate state is stored and what is lost or recomputed when a task fails, define retry granularity and how partial output is kept invisible, design the all-or-nothing output commit, and specify how a downstream consumer would safely ingest the job's output. Include rejected alternatives with reasoning.
3. **Implementation pass** — build a working prototype that demonstrates a parallel multi-stage job end to end (a grouped aggregation and a join over two sharded datasets), plus fault handling: kill a worker mid-task and show the job still completes with correct, non-duplicated output; fail a job partway and show no partial output is visible to consumers
4. **Review** — defend your reasoning in a reviewer session

## Scenario

You're a senior engineer on the data platform team at an online marketplace with about 15 million registered users. Every night the company needs to turn the day's raw data — roughly 90 million clickstream events (~40 GB of compressed logs landing in an object store) plus a snapshot of the user and product databases — into derived datasets: seller settlement reports, product recommendation tables, and aggregate analytics that the finance and product teams read every morning. The whole pipeline must finish within a 6-hour overnight window.

The current pipeline is a collection of Python scripts run by cron on a single beefy machine, and it has been the source of three painful quarters:

1. **The OOM wall**: the recommendations script builds an in-memory hash table keyed by user to join clickstream events against user profiles. As traffic grew, its working set outgrew RAM; the script now OOMs two or three nights a month, and each failure means rerunning the entire 4-hour job from the top. There is no notion of retrying at the granularity of a smaller unit of work, and nobody has confronted the choice between in-memory aggregation and disk-friendly sorting.

2. **The settlement double-pay**: the settlement script writes directly into the production PostgreSQL database, row by row, as it computes. One night it crashed halfway through, was rerun, and re-inserted rows it had already written — several sellers were paid twice, and finance spent a week reconciling. The job has no all-or-nothing output guarantee: partially completed runs are visible to downstream systems, and retries duplicate output. On top of that, the row-by-row writes hammer the production database hard enough that on-call gets latency alerts every night around 2 a.m.

3. **The silent stale dashboard**: the pipeline is really a chain of scripts — one script's output files are the next script's input — but the dependencies live in engineers' heads and cron start times. One night an upstream job ran long, a downstream job started anyway against the previous day's files, and the exec dashboard showed stale numbers for two days before anyone noticed. There is no workflow scheduler enforcing the DAG, and no way to tell which job in the chain broke.

Leadership has approved a small cluster (a handful of commodity machines plus the object store you already use) and wants the nightly pipeline rebuilt on a proper batch processing foundation. They are wary of adopting a heavyweight framework nobody on the team understands, so they want you to build — and be able to explain — the core engine yourselves: how work is parallelized, how the big joins actually happen, what occurs when a machine dies at 3 a.m., and how derived data gets back to production systems without ever repeating the double-pay incident.

Walk me through how you'd design the batch processing engine and the nightly pipeline that runs on it.
